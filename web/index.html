    What actually goes wrong

    1. The proxy starts forwarding

      Headers and part of the JSON body go out on a pooled keep-alive socket. The header said Content-Length: 45, so the upstream's parser now expects exactly 45 body bytes.

    2. The user sends a follow-up, so the browser aborts

      This is the normal path in a chat UI, not an edge case. The client is gone before the body finished uploading.

    3. The proxy drops the request but not the socket

      It stops forwarding and answers the client. What it never does is destroy its upstream request. Twenty-five body bytes were promised and never sent, and the socket goes back in the pool looking perfectly idle.

    4. The follow-up is written onto that same socket

      HTTP has no message IDs — it is a byte stream, and position is the only thing that distinguishes one message from the next. The upstream is still owed 25 body bytes, so it takes them from the front of the new request: 

      {"message":"Hello",POST /chat-stream HTTP/1.

      That is request #1's body now — a JSON fragment welded to a request line.

    5. The parser resyncs on garbage

      Having satisfied the body, it looks for a new request line and finds 1\r\nHost: …. It reads 1 as an HTTP method, gives up with HPE_INVALID_METHOD, and answers HTTP/1.1 400 Bad Request.

    The fix

    Propagate the client's abort to the upstream request. Destroying it takes the socket out of the pool entirely, so it can never be handed to the next request: 

    on: {  proxyReq: (proxyReq, req, res) => {+   const abortUpstream = () => {+     try { proxyReq.destroy?.(); } catch {}+   };+   req.on('aborted', abortUpstream);+   res.on('close',   abortUpstream);  },}

    The wider lesson: a proxy that is perfectly correct for request/response endpoints can still be wrong for streaming ones. Request/response traffic rarely aborts mid-body, so the bug stays hidden. Streaming aborts constantly — and every abandoned upstream request leaves a live socket holding a half-finished message.
